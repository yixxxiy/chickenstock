## 1. 项目目标与决策摘要

本轮目标是以较小工程改动，将现有游戏通过 Netlify 发布，使用 PostHog 观察玩家是否顺利开始、理解玩法、持续游玩，以及是否愿意通过反馈或等待获得重试机会。

### 1.1 已确认

| 项目 | 决策 |
| --- | --- |
| 发布平台 | Netlify，沿用站点 `https://chickenstock.netlify.app`，不新建站点 |
| 数据平台 | PostHog；用户已做过初步连通测试，可以使用 |
| 玩家范围 | 中国大陆与海外；分别验证网络、浏览器及数据送达 |
| 改动原则 | 不大改架构，不新增跨天回退；沿用“回到当天早晨”机制 |
| 首次加载目标 | 从点击链接到能开始操作尽量在十秒以内；需实际测量，不提前承诺 |
| 核心指标 | 加载成功率、可操作耗时、教程完成率、第一至第八天进入／完成漏斗、模式选择、重试入口选择 |
| 时间指标 | 1 分钟、3–5 分钟、5–10 分钟、10–20 分钟；底层记录 1／3／5／10／20 分钟节点 |
| 回访指标 | 增加 D1；D7 暂不列首轮验收指标 |
| 奖励形式 | 首次问卷换重试；完成问卷后使用约五秒占位等待，不接真实广告 |
| 入口文案 | 首次“填写反馈，获得重试机会”；后续“等待后重试” |
| 玩家画像 | 游戏水平、年龄段、性别、同类游戏经验，均允许不披露 |
| 反馈内容 | 重试原因，以及可选的一句话改进建议 |

用户希望五至十分钟参与表现能达到约 40%。这是内部探索目标，不是行业合格线；最终需分别约定五分钟与十分钟指标的验收目标。用户预计二十分钟内覆盖绝大多数测试者，这仍是待数据验证的假设，不能将计时截断在二十分钟。

## 3. 指标口径

### 3.1 加载与首次操作

页面外壳必须在启动 Godot 之前记录加载开始。仅在游戏 `_ready()` 后上报，会漏掉下载／初始化失败的玩家。

| 指标 | 口径 |
| --- | --- |
| 可观测加载成功率 | 产生 `game_ready` 的访问数 ÷ 产生 `page_open` 的访问数，按 `visit_id` 去重 |
| 首次可操作耗时 | 页面导航开始到主菜单／首个入口真实可操作的时间 |
| 进入游玩耗时 | 页面导航开始到 `play_start` 的时间，包含玩家自主选择时间，不能替代技术加载耗时 |
| 加载失败 | 能明确捕获的下载、引擎初始化、图形能力等错误，记录阶段与错误类型 |

限制：页面和统计脚本完全无法运行、被拦截、离线或拒绝采集时，访问也可能不可见。报表必须写“可观测访问”，不能宣称包含所有点击。缺少 `game_ready` 不自动等于确认崩溃，也可能是用户主动离开。

按版本、冷／热加载测试条件、大陆／海外测试来源、浏览器分别查看；来源未知单列，不用语言推断地区。看实际人数、耗时中位数与 P90，不能只看平均值。人工测试的“点击链接”耗时与浏览器可测的导航起点注明差别。

### 3.2 D0 分钟参与

建议正式报表命名为“首次游玩会话有效时长达标率”，产品讨论可简称分钟留存。

- 起点：首次进入可玩的教程或正式游戏。仅打开菜单不算开始游玩。
- 累计节点：60、180、300、600、1200 秒，各节点同一首次游玩会话只记录一次。
- 分母：首次开始游玩、且已具备相应观察时长的匿名玩家；临近报表截止的新玩家不能提前算流失。
- 分子：首次游玩会话中累计有效时间达到对应节点的匿名玩家。
- 教程计入；重玩、当天重试不清零本次会话累计时间；同时按教程／正式／结算等阶段记录时长。
- 后台、问卷、五秒占位等待不计入有效游玩时间。正常结算阅读单独记录；长时间静置停止累计。
- 自动生产存在时，不能简单要求每秒点击才计时。静置阈值及会话结束规则需实施前明确并版本化。
- 二十分钟后继续累计总时长；节点只是报表入口。

展示两类不同数据：

1. **累计达标率**：达到五分钟人数 ÷ 首次游玩人数。
2. **阶段继续率**：达到十分钟人数 ÷ 达到五分钟人数。

它们不能混为一个“5–10 分钟留存率”。总时长分布另保留 `<1`、`1–3`、`3–5`、`5–10`、`10–20`、`≥20` 分钟桶，避免漏掉一至三分钟玩家。

八日终局是游戏内进度事件，不是现实中的八日留存。三分钟完成后满意退出，与尚未理解玩法就退出，要结合终局／重玩事件区分。

### 3.3 D1 回访

建议口径：首次开始游玩的匿名玩家中，在次一自然日再次开始游玩的比例。

- 固定 PostHog 项目报表时区，实施前与用户确认；大陆与海外使用同一明确口径。
- 只统计完整经过次日观察窗口的首玩群组。
- 返回打开页面与返回实际游玩分开，后者用于主 D1。
- 明日开启新会话，不能把昨日页面跨午夜仍在运行当作一次主动返回。
- 不把“自然日 D1”与“首次游玩后 24–48 小时返回”混用。
- 未来如需首个 24 小时总时长，作为另一指标单独计算。

### 3.4 教程、进度、模式与重试

| 指标 | 分母／分子与注意事项 |
| --- | --- |
| 教程完成率 | 教程开始者中完成者；保留步骤 0–7 的到达、完成、耗时 |
| 每日进入／完成 | 按 `run_id` 观察第 1–8 天；同时提供玩家去重漏斗与重试次数 |
| 八日打完率 | 新开启八日挑战中出现第八天终局的局数 |
| 八日目标达成率 | 新开启八日挑战中终局同时满足资产 3000、鸡群 15 的局数；不等同打完率 |
| 模式选择 | 入口曝光 → 点击某模式 → 真正进入；续档与新局区分，模式从现有代码枚举 |
| 重试选择率 | 看到了可用入口的玩家中点击的比例；同时记录曝光／点击次数 |
| 重试恢复率 | 点击重试后实际成功恢复当天的比例 |
| 重试效果 | 恢复后的有效时长、继续下一天、最终结果、重复重试次数 |

没有阶段失败机制时，不得称“失败复活率”；现有日结重试也可能出于策略探索或追求更好结果。

## 4. 身份、持久化与缓存

### 4.1 三类记录独立

| 数据 | 存储与重置原则 |
| --- | --- |
| 游戏状态 | 沿用 Godot `user://` 存档；重开可清除 |
| 匿名统计身份 | 使用统一 PostHog `distinct_id`；不要再建立不一致的第二套身份；重开游戏不调用统计身份 reset |
| 问卷完成状态 | 独立于游戏进度保存；同一浏览器重新开局不重复要求画像 |

PostHog 支持 localStorage／第一方 Cookie 持久化；Godot Web 的用户文件持久化依赖 IndexedDB。开发中要验证浏览器确实允许持久化，不能只依赖内存状态。

- 普通刷新、关闭再开、Ctrl+F5 通常不清除上述网站存储。
- 游戏内重开只重置玩法记录，保留统计身份与问卷状态。
- 清除全部网站数据、无痕窗口关闭、换浏览器／设备，可能丢失匿名身份。
- 上报成功的 PostHog 历史事件不会因清缓存消失，但未来访问可能无法关联。
- 固定正式域名；不要让测试玩家频繁更换预览域名后期待身份自动连续。
- “每人一次问卷”是同一浏览器匿名身份下的一次；不承诺跨设备去重。
- 不采用设备指纹或偷偷恢复已被用户清除的身份。

### 4.2 标识分工

- `distinct_id`：匿名玩家，跨正常访问保留。
- `visit_id`：本次页面加载，用于加载成功率和耗时对账。
- `session_id`：游玩会话，不能与页面刷新完全等同；刷新续接、后台超时规则需明确。
- `run_id`：一局正式挑战／无尽经营；正常续档保留，重新开局更新。
- `attempt_id`／`retry_index`：同一天的尝试，用于区分当天回退，避免漏斗重复。
- `event_id`：发送重试时沿用，配合接收端支持的去重机制验证，不能重复产生计数。

## 5. 奖励重试与问卷

### 5.1 现有机制上的最小流程

```text
日结出现可用“回到当天早晨”入口
  → 记录入口曝光
  → 玩家点击
  → 尚未提交问卷：展示问卷
    已提交问卷：展示约五秒等待
  → 完成对应条件
  → 调用已有当天快照恢复
  → 恢复成功事件
  → 继续记录当天尝试与后续进度
```

入口文案必须描述真实行为：首次“填写反馈，获得重试机会”，后续“等待后重试”。不得将问卷、入口曝光、占位等待上报为真实广告展示或完播。

首次问卷是否可跳过并改等五秒，尚未确认。不要把前一位 AI 的推荐当成用户决定。问卷提交与“奖励已经发放”是两个状态；防止重复点击／回调导致重复恢复。网络异常或关闭页面后的补偿规则需在接入时设计，不要让问卷服务异常永久锁住游戏。

### 5.2 固定画像：用户明确要求保留

| 字段 | 问题与选项 |
| --- | --- |
| `self_reported_skill` | 你觉得自己的游戏水平如何？新手／休闲、进阶、高手／硬核、不想披露 |
| `age_bracket` | 年龄范围：18 岁以下、18–24、25–34、35 岁以上、不想披露 |
| `gender` | 男、女、其他、不想披露 |
| `genre_experience` | 你玩过类似的经营／放置点击游戏吗？从没玩过、几乎没玩过、偶尔玩、有时玩、经常玩、不想披露 |

“偶尔／有时”相近，但这是用户希望保留的选项；若简化需征求意见。画像字段使用稳定枚举，显示文字走中英文文案。未回答与主动“不披露”不得使用同一个值。

### 5.3 当次体验

**重试原因**，建议单选主因：

- 没看懂规则。
- 来不及操作。
- 买卖决策后悔了。
- 想试另一种玩法。
- 误触或卡顿。
- 其他。

**开放反馈**：“目前最希望改进什么？”可选填一句话。

固定画像保存为玩家属性，用于筛选／分群；原因与自由文本保存为反馈事件，带上版本、触发来源、模式、天数、结果。需要配置并验证匿名玩家属性可以用于 PostHog 分析；不要用随机账号身份伪装登录。

### 5.4 触发位置与频率

| 位置 | 处理原则 |
| --- | --- |
| 初次进入／新手引导 | 不弹问卷 |
| 当天重试入口 | 首次问卷，已提交后等待；具体跳过规则待确认 |
| 设置菜单 | 建议提供自愿反馈入口，避免只有重试玩家能反馈 |
| 第八天通关／失败 | 用户要求考虑反馈；先完整展示结算，不自动遮挡 CTA；展示形式与频次待确认 |
| 挑战每次检查失败 | 当前未找到对应实现，确认版本后再接入 |
| 第二十天挑战通关 | 当前未找到对应实现，不自行新增 |

“只填一次”究竟限制画像还是整份反馈仍待确认。推荐画像一次、后续反馈自愿，但尚未获明确确认。六项内容不要挤成一个手机长弹窗；可拆步骤，问卷与游戏原有层级／输入边界需验证。

### 5.5 数据解释与最小采集

- 只分析自愿提供的画像；不推断缺失年龄／性别。
- 结算／重试才填问卷会造成样本偏差：早离开的玩家更可能没有画像。报告显示回答覆盖率和各分组样本数，不能将回答者代表全体玩家。
- 小样本避免年龄×性别×水平×经验的多重交叉，先单维度比较。
- 简要说明画像用于优化游戏与分组分析，不采集姓名、精确生日、联系方式或存档全文。
- 自由文本限制长度并提示不要填写个人联系方式；明确访问权限与保留规则。
- 宽年龄段和“不披露”选项不自动等于满足全部地区隐私要求；针对实际发布人群另核对适用要求，不在本文作合规保证。

## 6. 推荐接入结构

```text
自定义 Web 导出外壳
  ├─ 访问、加载、页面可见性、统计身份
  ├─ PostHog SDK：异步、精简功能
  └─ 问卷网页层／桥接回调

Analytics.gd：统一事件入口、上下文、去重、有效计时
          ↑
Game.gd / SettlementCard.gd 中少量明确的状态事件
```

### 6.2 可靠性约束

- SDK、统计请求不阻塞游戏启动；未配置或非 Web 环境应安全退化。
- 默认不启用会话回放／全量自动点击采集；Godot 画布的玩法语义主动上报。
- 用计时器／单调时钟计算有效时间，低频心跳辅助诊断；不逐帧发送事件。
- 页面隐藏／恢复时处理计时边界，不依赖关页最后一次请求。
- 批量队列与重试有上限；失败不得无限增长内存／本地存储；同事件重试保持标识。
- 状态确实成功后再发成功事件；重复刷新结算卡不是又一次通关。
- 日结曝光、进入终局、奖励完成分别去重。游戏重置不删除玩家身份。
- 问卷显示时隔离游戏输入，关闭／恢复后正常操作；不得拆现有 ScreenTouch 吞事件、防抖与结算层级。
- 测试问卷覆盖当前 COOP／COEP 请求头下的跨域加载与回调；不得为方便接 SDK 删掉项目要求的请求头。
- 客户端只使用适合公开的项目采集 token；不写入 PostHog 私人管理密钥或 Netlify 部署凭证。

## 7. 第一期事件字典草案

以下是建议的精简名称；尽量复用旧 `ANALYTICS.md` 的已有名称。实施前统一，不同时发送同义事件。

| 事件 | 触发点／关键属性 |
| --- | --- |
| `page_open` | Web 外壳开始；`visit_id`、版本、来源 |
| `game_ready` | 首个入口真实可操作；`load_ms` |
| `load_error` | 可捕获的加载错误；`stage`、`error_type` |
| `menu_view` | 菜单可见，作为模式入口曝光 |
| `menu_click` | 玩家选择；`item` |
| `play_start` | 实际开始教程或正式玩法；用于首玩／D1，含 `mode` |
| `run_start` | 正式新局或续档进入；`run_id`、`continued`、`mode` |
| `tutorial_start` | 教程开始 |
| `tutorial_step_view` | 某步骤真正展示；`step` |
| `tutorial_step_complete` | 动作成功并推进；`step`、`step_duration_ms` |
| `tutorial_finish` / `tutorial_abort` | 完成或退出；`duration_ms`、最后步骤 |
| `day_start` | 第一日以及后续日开始；`day`、`attempt_id`、`entry_reason` |
| `day_end` | 日结数据确定；`day`、`how`、结果摘要、尝试标识 |
| `campaign_end` | 首次完成八日终局计算；`quest_ok`、资产、鸡数 |
| `settlement_cta` | 下一天／重开／继续无尽等实际选择 |
| `playtime_milestone` | 达到节点；`seconds`、是否首次游玩会话 |
| `playtime_heartbeat` | 低频累计有效时长与当前阶段；不是逐帧事件 |
| `retry_offer_view` | 可用入口实际显示；`offer_id`、`day`、`reward_type` |
| `retry_offer_click` | 点击对应入口；同一 `offer_id` |
| `survey_view` / `survey_submit` / `survey_dismiss` | 问卷版本、来源、结果；提交不等于奖励发放 |
| `retry_wait_start` / `retry_wait_complete` | 五秒占位等待；不计作广告 |
| `retry_restored` | 当天快照实际恢复成功；新尝试标识、重试次数 |

公共字段按需带 `build`、`schema_version`、`lang`、`visit_id`、`session_id`、`run_id`、`mode`、`day`、`attempt_id`、`event_id`、测试环境标记。不要每条事件都附完整游戏状态或自由文本。首轮不扩展到每次收蛋、长按 tick 的全量日志。

## 8. 包体与兼容性计划

不必等 UI 永久定稿再优化；每个发布版本需要固定资源、核对引用并回归。

### 8.1 本地资源观察值

| 资源 | 源文件大小约值 |
| --- | --- |
| assets 全目录，含草稿／对版 | 110.74 MiB |
| 主地图 `farm-background.png` | 8.73 MiB |
| 当前完整字库 `game_zh_full.otf` | 8.31 MiB |
| 已有精简字库 `game_zh.ttf` | 0.19 MiB |

这些不是正式 PCK 或网络传输量。不能承诺用旧精简字体替换就能安全减少 8 MB；必须重新覆盖当前文案、动态符号与新增问卷文本，验证无缺字。网页问卷字体与 Godot 字体分别核对。

### 8.2 优先顺序

1. 正式导出基线：记录 HTML／JS／WASM／PCK 大小、实际压缩传输量、下载与初始化阶段耗时。
2. 核对导出排除项和运行时动态资源引用，剔除未使用资源进入发布包，保留源素材。
3. 检查地图尺寸／导入压缩及字体子集；每项优化单独量化并视觉验证，不顺手改画风。
4. 检查 Netlify 压缩、缓存及版本更新行为；不只看本地文件大小。
5. 若仍超目标，再提出定制引擎模板／分包方案，不直接进行高成本改造。

首轮覆盖大陆微信内置浏览器、大陆手机浏览器、海外 iPhone Safari、Android Chrome，并包含较低性能手机。按实际设备／网络记录结果，标记尚未覆盖的范围。单线程保持不变；Godot Web 的 WebAssembly／WebGL2 能力要求仍限制兼容性。
